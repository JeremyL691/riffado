---
title: Backup and restore
description: Export your recordings or restore a self-hosted operations backup.
---

Riffado has separate export and operations-recovery paths:

- **`/api/backup`** creates a full-data ZIP for taking your data with
  you. Its manifest describes whether each recording's audio,
  transcript, timeline, and summary were included. `timeline.json`
  keeps timestamp provenance and per-segment correction details.
- **`/api/export`** flattens transcripts into one human-readable
  `txt`, `srt`, `vtt`, or `json` file. It is for handing transcript
  text to other tools.
- **Operations backup** is the consistent Postgres dump, audio and
  storage volumes, SQLite-consistent pipeline database backup, and
  pipeline work directory used to restore a self-hosted service.

## Full-data ZIP export

**Settings → Export/Backup → Create Backup** (or `POST /api/backup`)
produces a ZIP containing `manifest.json` and a folder for each
recording. A folder can include `audio.<ext>`, `transcript.txt`,
`timeline.json`, and `summary.json`. The manifest records which files
were included. If any recording's audio is missing or unreadable, the
export worker marks the job failed, discards the partial ZIP, and does
not send a ready notification. Check the manifest when verifying an
archive produced by the builder or another compatible tool.

The ZIP is **plaintext** because Riffado decrypts your fields before
serialization. Restrict access, store it encrypted, and do not email it.
Keep the export separate from the encryption key. The ZIP does not
contain the key and is not a server restore package.

## Transcript export

`GET /api/export?format=<fmt>` flattens every one of your recordings
into one file:

| Format | Content |
| ------ | ------- |
| `json` | One JSON document with every recording and transcript |
| `txt`  | Plaintext, one block per recording |
| `srt`  | SubRip subtitles for all recordings |
| `vtt`  | WebVTT subtitles for all recordings |

## Operations restore

There is no ZIP import endpoint. Restore an operations backup into an
isolated self-hosted stack using the Postgres dump, audio and storage
volumes, pipeline SQLite backup and work directory. Restore the matching
`ENCRYPTION_KEY` from its separate secure storage. Disable automatic sync
and external provider access during verification. Compare recording and
transcript counts and hashes, summary hashes, audio hashes, timeline
provenance, and correction metadata before returning the restored stack
to service.

The ZIP is an export artifact; uploading it does not recreate database
records. See the [long-audio operations runbook](../../../docs/audio-pipeline-operations.md)
for the isolated restore and export verification procedure.

## What's encrypted vs. plaintext

- **In the database**, sensitive fields are encrypted at rest with
  AES-256-GCM (see [Encryption at rest](../reference/encryption-at-rest)).
- **In a ZIP from `/api/backup`**, those fields are decrypted before
  serialization. Protect that file as plaintext personal data.
- **Audio in storage** is not encrypted by Riffado's app-layer
  encryption. Use bucket-level server-side encryption when needed.
